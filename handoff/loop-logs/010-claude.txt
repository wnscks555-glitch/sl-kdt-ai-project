리뷰 010의 높음 1건과 중간 4건을 처리했습니다. 4건은 반영했고, M4는 코드를 바꾸지 않고 명세 이견으로 남겼습니다. 수정 후 `py -m unittest discover -s tests`를 실행했고 138개가 모두 통과했습니다(기존 134개 + 새 테스트 4개, 종료 0). 다만 평가 보고서는 다시 만들지 못했습니다. 저장된 보고서에는 새 보류 열이 없습니다.

| 항목 | 처리 | 내용 |
|---|---|---|
| H1 | 반영 | 오류 주입 단계에서 `EQUIP_RESTART` 행을 건너뛰는 조건을 재가동 모드일 때로 좁혔습니다(`src/generate.py`). 이전 모드에서는 일반 공정명입니다. 회귀 테스트는 이 공정명과 다른 이름으로 생성한 CSV가 같은지 비교합니다. |
| M1 | 반영 | 재가동 모드에서 검사에 쓸 설비가 설비 파일에 하나도 없으면, 끝없이 기다리지 않고 오류를 냅니다. 생성·평가 명령은 종료 코드 2로 끝나고 보고서를 만들지 않습니다. 이전 모드의 흐름은 그대로입니다. |
| M2 | 반영 | 실행별 `held`와 집계 `mean_held` 열을 추가했습니다(터미널 표 포함). T63 테스트에 보류 평균 13.73 단정을 더했고 기존 단정은 그대로 두었습니다. 이전 구현 기록의 "T63을 그대로 재현했다"는 과장이었다고 로그에 적었습니다. |
| M3 | 반영 + 명세 이견 | 검출률 분모를 명세대로 실행 수로 바꿨습니다. 고장 설비가 2대 이상이면 "하나 이상 검출"과 "모두 검출" 중 무엇인지 명세에 없어서, 평가가 그런 설정을 종료 코드 2로 거절합니다. 고장 설비가 1대인 제출 결과는 값이 그대로입니다. |
| M4 | 보류 + 명세 이견 | 최종 CSV 행 기준으로 맞추려면 생성 단계와 오류 주입 단계를 합쳐야 하고, 그러면 평가 결과 전체가 바뀝니다. 그래서 코드는 두고 README에 단위만 밝혔습니다: `delay_rows`는 오류 주입 전 정상 행 기준이고, 최종 CSV에서는 정지와 재가동 사이가 30행보다 길 수 있습니다. |

**정하실 것 두 가지(명세 이견, `handoff/gpt-log.md`에 기록):**
- **M3:** 고장 설비가 여러 대일 때 검출률을 "하나 이상 검출한 실행"으로 셀지, "모두 검출한 실행"으로 셀지.
- **M4:** `delay_rows`를 정상 생성 행 기준으로 인정할지, 최종 CSV 행 기준으로 바꿀지.

**다시 만들지 못한 것:** 테스트 명령 말고는 셸 실행이 거부되어 `reports/eval_dev_*`, `eval_holdout_*`, `eval_baseline_*`와 `handoff/run-logs/stage5-*.txt`를 다시 만들지 못했습니다. H1·M3 수정이 기존 열 값을 바꾸지 않을 것으로 보고 있지만, 다시 계산해 확인하지는 않았습니다. README 「평가」 절의 명령 세 개로 다시 만들어야 합니다.

`handoff/gpt-log.md`에 항목별 처리 이유와 테스트 출력 원문을 붙였습니다. 커밋은 하지 않았습니다.
