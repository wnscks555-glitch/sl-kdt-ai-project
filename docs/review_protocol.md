# AI 작업과 독립 검토 절차

상태: 2026-09-30 계획. [v6](../../outputs/제조기술개발_프로젝트_주제와핵심기능_v6.md)와 [요구사항 R1–R8](requirements.md)을 기준으로 한다. 사용자와 작업 범위를 확인한 뒤 구현을 시작한다.

## 역할과 모델 사용

| 역할 | 권장 선택 | 할 일 |
| --- | --- | --- |
| 작업 담당 | 범위가 좁은 파일·표시·문서: Luna Medium. 상태 전환·재검사 연결처럼 규칙이 맞물린 부분: Sol Medium | 지정 범위의 코드 작성·관련 실행·결과 기록 |
| 독립 검토 | G0·G2·G3: Sol High. 중대한 설계 충돌이 남을 때만 Astra High 또는 선택적인 Claude 검토 | 요구사항·원자료·코드·실행 결과 대조. 읽기 전용 검토 |
| 사용자 | 모델과 무관 | 범위·예상 결과·채택 여부 결정. AI 제안과 실제 결과 비교. 핵심 코드 흐름을 설명할 때까지 질문 |

작업 담당과 검토 담당은 가능한 한 **서로 다른 채팅**으로 둔다. 더 높은 모델의 동의만으로 검증이 끝난 것은 아니다. 남은 주간 사용량 67%는 작업 횟수나 보장되는 개발 시간으로 환산하지 않는다.

## 검토 관문

| 관문 | 검토 자료 | 통과 조건 |
| --- | --- | --- |
| G0: 명세 | v6, R1–R8, S1–S9, 입력 필드와 ID 규칙 | 완료·보류·재검사 결과가 예상대로 정해져 있고 중요한 모호성 해소 |
| G1: 최초 통합 | 제품 등록·조립·두 검사·FAIL 보류의 실행 결과 | 정상·미실시·FAIL의 상태와 이유가 추적 가능. 사용자 설명 가능 |
| G2: 재검사 통합 | 코드, S1–S9 입력·예상·실제, 이력, 실행 방법 | 유효한 새 PASS만 보류 해제, 이전 FAIL 보존, P0/P1 문제 해소 |
| G3: 최종 | 처음부터 재실행한 결과, 사용법, 시연, 한계와 AI 활용 기록 | 완료 주장과 실제 실행 범위 일치, 필수 흐름 시연 가능 |

G1은 사용자 점검으로 시작한다. G0·G2·G3에서 상위 모델 검토를 우선 요청한다. 중대한 수정이 생기면 바뀐 부분과 관련 정상 흐름만 재검토한다. 작은 문구 차이로 검토 회차를 늘리지 않는다.

## 작업 완료 보고 묶음

구현 담당이 완료를 주장할 때 아래를 **짧게** 남긴다. 실제 실행 결과는 `results/runs/`, 선택한 화면 증거는 `evidence/`에 둔다.

1. 작업 ID와 연결 요구사항·시나리오 ID.
2. 변경 파일과 실행 방법.
3. 실행 입력, **사전에 정한 예상**, 실제 출력과 실행 시각.
4. 성공·실패·미실행 항목과 오류 원인.
5. 남은 가정·위험과 사용자 결정이 필요한 점.

검토 담당에는 전체 대화 원문 대신 v6, 관련 요구사항, 변경 파일, 이 보고 묶음을 전달한다.

## 구현 담당에게 보낼 기본 지시문

> 이번 작업은 [작업 ID]이며 [R/S ID]만 구현해 주세요. 기준은 v6와 `docs/requirements.md`입니다. 수정 가능한 파일은 [경로]입니다. 사용자 결정이 필요한 가정은 먼저 표시하고, 정해진 범위에서 구현·실행해 주세요. 완료 보고에는 변경 파일, 실행 방법, 사전 예상과 실제 결과, 미실행 항목, 남은 위험을 포함해 주세요. 실제 SL 검사·성능을 주장하지 마세요.

## 상위 모델에게 보낼 읽기 전용 검토 지시문

> 이번 검토 관문은 [G0/G2/G3]입니다. v6와 `docs/requirements.md`의 관련 R/S ID를 작업 완료 보고와 실제 변경 파일에 대조해 주세요. **파일을 수정하지 말고** 예상과 실제가 맞는지 확인해 주세요. 가능하면 관련 실행 경로를 직접 확인하고, 실행하지 못한 것은 미확인으로 표시해 주세요. 문제는 심각도(P0: 핵심 결과 불가, P1: 잘못된 상태 판단·요구 위반, P2: 작은 개선), 재현 입력, 기대/실제, 파일 위치와 수정 방향으로 보고해 주세요. 문제가 없을 때도 확인한 범위를 적고 실제 SL 성능을 입증했다고 표현하지 마세요.

P0/P1은 수정·재확인 후 통과한다. P2는 기록하고 미룰 수 있다. 모델 의견이 갈리면 **요구사항·모의 입력·실제 출력**을 기준으로 사용자가 결정한다.

## 사용자가 매 관문에서 이해할 내용

- 왜 본조립 전에 검사가 유효하지 않은가?
- FAIL `L1`을 요청 `R1`과 재검사 `L2=PASS`가 어떻게 연결하는가?
- 왜 검토 메모나 요청만으로 보류가 해제되지 않는가?
- 이전 FAIL은 어디에 남고, 현재 상태는 어떤 사건들로 설명되는가?
- AI가 제안한 반례 또는 코드 중 내가 수정·기각한 한 가지는 무엇이며 실행으로 어떻게 확인했는가?

사용자는 직접 코드를 작성하지 않아도 이 질문과 한 개의 입력 변경에 따른 예상 결과를 설명할 수 있어야 면접에서 자신의 판단과 AI의 작업을 분명하게 말할 수 있다.
